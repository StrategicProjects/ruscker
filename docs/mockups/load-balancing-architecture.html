Balanceamento de carga (nível 1)
Como o proxy decide para qual réplica enviar uma nova sessão. Para apps Shiny, a sessão fica presa nessa réplica até expirar (sticky session). Para APIs, cada requisição é roteada independentemente (round-robin).
O que aconteceu: Visitante C abriu a Aurora Prime sem cookie de sessão. O proxy consultou o estado das 3 réplicas, escolheu a R2 (menor utilização), criou uma sessão e gravou um cookie __ruscker_session assinado. As próximas requisições do visitante C vão direto para R2 sem reconsultar o roteador.
As três camadas
implementado

1. Pool de réplicas por spec

Cada spec containerizada tem um pool de réplicas (containers idênticos) controlado por min-replicas / max-replicas. O auto-scaler liga novas réplicas quando a utilização passa de scale-up-threshold e desliga após scale-down-grace segundos sob o limite inferior.

Drenagem espera sessões acabarem antes de matar o container.

fase 6

2. Multi-host (opcional)

Para deploys maiores: um MultiHostDockerBackend distribui containers entre vários servidores Docker. Suporta as estratégias bin-pack (preencher um host antes do próximo) ou spread (espalhar para tolerância a falhas).

O proxy escolhe a réplica como sempre — o host onde ela vive é transparente.

fase 7

3. HA do próprio Ruscker

Dois ou mais processos Ruscker atrás de um balanceador L4 (HAProxy, nginx, ELB), com estado compartilhado em Postgres.

Qualquer instância serve qualquer sessão. Failover transparente quando uma cai. Indicado para deploys críticos onde reiniciar Ruscker não pode pausar o portal.
