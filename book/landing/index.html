◆ Rust · container portal

Your Shiny, Streamlit and API containers, behind one small binary.

Ruscker hosts and load-balances containerized apps behind a single proxy — with a catalog people can find things in, an admin panel to run it from, and sign-in for the systems around it. It reads the ShinyProxy YAML you already have.

A portal, a proxy and the panel to run them

One process serves the landing page and the admin, and reverse-proxies each visitor to an app container it starts on demand through the Docker daemon. No JVM, no Node, no separate database to operate.

📦

One static binary

About 14 MB of memory when idle, instant start, no runtime to install. Ships as a .deb with a hardened systemd unit, a musl tarball, a signed container image and a Homebrew formula.

🔁

ShinyProxy-compatible YAML

The field names you already use keep working, and validate --strict-compat reports anything that is not supported instead of ignoring it. Import the file once; from then on the catalog lives in the admin.

⚖️

Load balancing that fits the app

Sticky sessions and WebSockets for Shiny and friends, seats per container, replicas spawned when the load asks for them and reaped when idle. Apps start cold on the first visit, behind a splash page.

🛠️

An admin panel you will use

Apps, media, credentials, users and groups, scheduled jobs, live CPU and memory per replica, logs, disk and volumes, an audit trail — and an appearance editor for the portal itself.

🔐

Access and sign-in

Apps visible per user and per group, two-step verification, identity passed to apps in headers they can trust. And Ruscker can be the sign-in provider (OpenID Connect) for other systems.

🩺

Looks after itself

A container that dies outside Ruscker is noticed and replaced; a failed start is cleaned up. The package brings an updater that verifies each release and goes back if the new one does not come up.

How it works

Browsers and API clients reach one Ruscker process. Everything else is containers it starts and stops for you.

01

Describe the app

An image, a port, who may see it. In the admin form, or imported from YAML.

02

Someone opens it

No replica yet? Ruscker asks Docker for one and shows a splash until it is ready.

03

Route the session

A signed cookie keeps the visitor on their replica; WebSockets and URLs are handled on the way.

04

Scale and reap

More visitors than seats starts another replica, up to your limit. Idle ones are removed.

Install & run

Pick the packaging that fits the host. Packages for amd64 and arm64 are attached to every release; changes between versions are in the release notes.

Debian / Ubuntu

$ sudo apt install ./ruscker_<version>-1_amd64.deb
$ systemctl status ruscker
$ curl http://localhost:8080/healthz

# your admin token
$ sudo grep RUSCKER_ADMIN_TOKEN \
    /etc/ruscker/ruscker.env

Homebrew (macOS / Linux)

$ brew install strategicprojects/tap/ruscker

Static binary

$ tar -xzf ruscker-<version>-linux-amd64.tar.gz
$ sudo install -m 755 \
    ruscker-<version>-linux-amd64/ruscker \
    /usr/local/bin/ruscker

Sign in with Ruscker

The portal already knows your people, their groups and their second factor. Turn on the provider and other systems can sign them in through it — authorization code with PKCE, per-client access groups, an audit of every sign-in. Client packages do the protocol for you.
